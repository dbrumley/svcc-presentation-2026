SLIDE 14  [14 / 38]
Anatomy of a Cyber Reasoning System.
------------------------------------------------------------------------------
Architecture of autonomy — how you actually build a Cyber Reasoning System (this is Mayhem, the system we built that won). Build it bottom-up on screen: (1) FOUNDATION — a Binary Analysis Platform that works on binaries, no source: disassembler, container parser, an instruction lifter to a formal model. (2) On top, OFFENSE (sword): fuzzing, symbolic execution, crash triage, automatic exploit generation (AEG), crash explorer — find and PROVE bugs. (3) DEFENSE (shield): data-flow analysis, hardening, crash-specific patches, static binary rewriting — patch without source. (4) On top of it all, the AUTONOMY AI — strategy: resource allocation and the patch chooser. THAT top layer — deciding what to do next — is the brain, and it's exactly where Era III intelligence goes. Then fuzzing and patching (next slides) are zoom-ins on two of these components. [~17:00]

SLIDE 16  [16 / 38]
And patch the binary — block the exploit.
------------------------------------------------------------------------------
Patching (the defensive half). The patch is LOCALIZED — the fix sits right where it crashes, on the backtrace: before the copy, check the length and exit if too long; same bug, same exploit input, now it hits the guard and the shell never pops. (Shown in C for clarity; in CGC the equivalent guard was applied straight to the binary, no source.) Seed for Era III (the muted line): localized patches are the EASY case — automated patchers and LLMs do well here. The OPEN problem is non-localized / root-cause fixes, where the fix isn't on the backtrace: (A) upstream — an integer-overflow size calc that feeds a later OOB write; (B) off-stack — a use-after-free freed in a different event; (C) a shared helper that must be fixed for all callers. LLMs do poorly the moment the fix leaves the backtrace. [~17:45]


SLIDE 17  [17 / 38]
The brain plays the players.
------------------------------------------------------------------------------
The brain — strategy (autonomy + counter-autonomy). Finding/exploiting/patching is capability; the bottleneck is the STRATEGY of what to do with it. Diagram = ricochet: attacks are visible on the wire, so Mayhem could capture a rival's exploit (Rival A) and replay it against another (Rival C) — you don't even need to find the bug yourself. Two more strategic levers: (1) timing the patch — deploying a fix LEAKS the bug (APEG: patch-based exploit generation), so sometimes you attack before you patch; (2) order — hit the weak players first. This is the top 'brain' layer of the architecture in action, and the work behind it ('How Shall We Play a Game?', Bao/Shoshitaishvili/Wang/Kruegel/Vigna/Brumley, IEEE CSF 2017) won an NSA Science-of-Security award; modeled as a partial-observation stochastic game, solved for the Nash-equilibrium strategy. [~18:15]

SLIDE 28  [28 / 38]
Evidence exploits aren't memorized.
------------------------------------------------------------------------------
Anecdotes — not memorization, research (from Seunghyun Lee's blog, who reads every transcript). Three Mythos runs: (1) CVE-2023-6702 (the MAIN case, with depth) — the bug is a type confusion between a 4-byte hash and a V8 heap pointer, exploitable because pointer compression makes BOTH 32 bits. STEP 1 recover: Math.random() is xorshift128+, a 128-bit LINEAR PRNG; object hashes derive from its stream via MurmurHash3, so from a few outputs you solve for the generator state (GF(2)-style; in practice an SMT/Z3 step handles the nonlinear '+') and the next hash is known in advance. STEP 2 weaponize (the bridge): a hash you can PREDICT is a pointer you CONTROL — forge a fake object inside the cage, corrupt a BytecodeArray, run arbitrary bytecode, ROP out of the sandbox. The original v8CTF author had dismissed this exact RNG-prediction plan as too complex. (2) CVE-2024-7965 — public work said the JIT bug was ARM64-only / too hard on x86-64; Mythos found a NEW WebAssembly+Turbofan path past where all public work stops. (3) CVE-2024-0519 — an in-the-wild bug with NO public report or PoC, a 'cold case' unreproduced for a year; Mythos reproduced it in a single 129-turn episode. Point: this is discovered, not recalled — work on par with an elite human researcher (callback to slide 9). Sets up the open questions next: patching, then strategy. [~25:00]

SLIDE 31  [31 / 38]
What seems hard still today.
------------------------------------------------------------------------------
Root cause — the Era III frontier (defense side). Localized patches (fix at the crash, on the backtrace) are SOLVED. The open problem: the real fix is often NOT on the backtrace. Two examples on screen — (1) double free: the abort is at the second free(obj), but obj was already freed in on_close(), a different event that isn't on this stack at all; the real fix is ownership/lifetime, elsewhere. (2) missing filter: the crash is at the use, but the validation belongs upstream in parse(), shared by every caller. Today's LLMs patch the crash frame and miss the cause. The Era III payoff: 'is the fix at the root cause?' is MEASURABLE — so it's TRAINABLE, exactly the ExploitBench move applied to defense. (Draft — reposition within Part III as you build it.) [~26:45]


SLIDE 32  [32 / 38]
The new job: writing oracles.
------------------------------------------------------------------------------
Slide [C] — intro to RL, define the nouns. ENVIRONMENT = target + harness (the V8 build, the fuzzer, the crashing input). POLICY = the model proposing a patch. ORACLE (the reward) = what scores the patch. The loop only works if the oracle is right. Offense's oracle is free — did the exploit fire? Defense has none. The exit(0) example IS reward hacking: hand the model a fuzz backtrace with a naive oracle (does it still crash?) and the cheapest winning move is exit(0) at the crash site — no crash, oracle says PASS, program is dead. Or exit(0) on every path: fuzzer goes green, software is gone. THE NEW JOB for security: writing oracles — reward functions that capture real correctness. We have great offense oracles, almost none for defense. Sets up the next slide: the oracle IS the measurement. [~27:30]
